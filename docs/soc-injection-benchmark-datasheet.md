# Datasheet: SOC-domain prompt-injection benchmark v1.0

**Issues #35/#37 (M3.1/M3.3).** Follows the Gebru et al. (2021), "Datasheets
for Datasets" template.

## Abstract (200 words)

This benchmark evaluates prompt-injection detectors in a security-operations-centre
(SOC) alert-triage setting, where an LLM-assisted pipeline reads structured
alert fields that may contain attacker-influenced text. It supersedes an
earlier 40-example, single-author corpus that this project's own paper
already flagged as too small to support a generalisation claim: the regex
detector's patterns and the corpus's injection strings shared one author, so
a 5% recall figure measured self-consistency rather than attacker realism.
This benchmark is 500 rows: 400 template-generated attack examples spanning
seven named families (direct override, role-play, buried/passive
instructions, encoded/obfuscated payloads, cross-field fragmentation, false
evidence injection, and output-format manipulation), plus 100 real benign
alerts from the Microsoft GUIDE dataset, selected as the cases a deployed
Random Forest classifier is least confident calling benign. It is released
under the MIT licence alongside the family-definition rubric, an interrater-
reliability worksheet, and the scoring code used to produce every number
reported against it — so a reader can reproduce or extend the evaluation
rather than take its numbers on trust.

## 1. Motivation

**For what purpose was the dataset created?** To measure whether input-side
prompt-injection detectors generalise beyond a small, self-authored test set.
The project's paper (`docs/final-report.md`, Limitations) explicitly names
this as an open gap: a 40-example corpus where the regex detector's author
and the corpus's author are the same person cannot distinguish "the filter
works" from "the filter matches its own author's phrasing."

**Who created it?** Built for this project (CNIT/PNTLab Pisa, TECIP, Scuola
Superiore Sant'Anna, AI Security Internship 2026) in response to an
independent review's Direction B caveat, quoted in issue #35: "Guardrail
domain transfer could become strong research but needs a much larger dataset
than 40 hand-authored examples."

**Who funded it?** No external funding; produced as part of the internship's
milestone M3 (issue #35), due 2026-09-12 per the supervisor-set schedule.

## 2. Composition

**What do the instances represent?** Each row is one alert-field value: a
synthetic attack payload (400 rows) or a real GUIDE `BenignPositive` alert's
`AlertTitle` value (100 rows).

**How many instances?** 500 total. Family breakdown (from
`experiments/results/m3_1_benchmark_generation.json`):

| Family | Definition | Count |
|---|---|---|
| F1 | Direct Override | 60 |
| F2 | Role Playing | 55 |
| F3 | Passive/Buried | 60 |
| F4 | Encoded/Obfuscated | 55 |
| F5 | Cross-Field Fragmentation | 50 |
| F6 | False Evidence Injection | 60 |
| F7 | Output-Format/JSON Manipulation | 60 |
| BCONTROL | Real benign GUIDE alerts | 100 |

**Attributes.** `benchmark_id, family, modified_field, original_value_snippet,
injected_payload, is_benign_control, expected_verdict_if_successful, notes`
— see `docs/soc-injection-benchmark-rubric.md` for full field definitions.

**Missing data.** None by construction — every row has all 8 columns
populated (`expected_verdict_if_successful` is the literal string `"varies"`
for format-only F7 attacks whose effect depends on how a downstream parser
handles the manipulated output, not a missing value).

## 3. Collection process

**How was the data acquired?** The 400 attack rows are generated by
`experiments/m3_1_generate_benchmark.py` from a template bank per family
(phrasing/encoding variants × target verdict × targeted field), combined
combinatorially and truncated to the required count — not hand-typed one row
at a time, but authored content nonetheless, in the same "self-authored
synthetic" tradition the smaller corpus it replaces already used and
disclosed. The 100 BCONTROL rows are real: reservoir-sampled from
`datasets/GUIDE_train.csv`'s `BenignPositive` rows (one per `IncidentId`,
260,495 unique incidents considered), scored by the deployed classifier's
prediction entropy, and the 100 highest-entropy rows kept.

**Time frame.** Generated 2026-09-09, seed 42, git commit at generation time
recorded in `experiments/results/m3_1_benchmark_generation.json`.

## 4. Preprocessing / cleaning / labelling

**Is there a label?** `is_benign_control` (bool) and `family` together give a
binary attack/benign label plus a 7-way family label for every attack row.

**Interrater reliability.** A blinded 100-row subset (50 attack / 50 benign,
`experiments/results/m3_1_rating_worksheet.csv`) and a Cohen's-kappa scoring
script (`experiments/m3_1_interrater_kappa.py`) exist. Per the supervisor's
request of 21 Sep, the subset is also issued as two per-rater sheets
(`experiments/results/m3_1_rating_sheet_raterA.csv` and `…raterB.csv`,
identical items in identical order, blank `verdict` column) alongside a
self-contained rater packet, `docs/m3-1-rater-instructions.md`. Neither sheet
carries `benchmark_id`, `family`, `is_benign_control`, or the modified field
name — `tests/test_m3_1_rating_sheets.py` asserts that on every build.
Scoring reports raw agreement, Cohen's κ, the disagreement count, and the
disagreement distribution across benign/F1–F7.

**The actual two-rater labelling pass has not been done as of this
datasheet's initial commit** — it needs two independent human raters, and a
single rater (or an AI system) re-checking its own generated labels would not
be independent by construction. Target once both raters complete the
worksheet: κ ≥ 0.75 (issue #35's acceptance criterion). This is stated as
pending rather than filled with an invented number, consistent with how issue
#32 (Kaggle tooling access) was handled elsewhere in this project before it
was resolved. Raters and timeline requested from the supervisors in
[issue #35's comments](https://github.com/AI-Security-Internships-2026/02-soc-copilot-threat-analysis/issues/35);
this section will be updated with the real κ once both rating passes land.

**What κ from this subset can and cannot establish.** Read bias 5 below
before quoting the number. All 50 benign rows in the subset are numeric GUIDE
field codes and all 50 attack rows are natural-language payloads, so the two
classes are separable on surface form alone. A high κ therefore confirms that
the binary labels are unambiguous to independent readers; it does **not**
establish that the rubric discriminates well on hard cases, and it is not
evidence about detector difficulty. The informative rows are the F3
(passive/buried) items, where the payload is plausible analyst prose — the
per-family disagreement breakdown is reported precisely so this can be read
directly rather than hidden inside the pooled statistic.

## 5. Known biases

At least five, stated plainly:

1. **The attack rows are template-generated, not drawn from real attacker
   traffic.** Phrasing diversity is bounded by the template banks in
   `experiments/m3_1_generate_benchmark.py`; a real adversary's phrasing
   distribution is unknown and likely wider.
2. **English-only.** No multilingual attack variants.
3. **Class imbalance by construction.** 400 attack rows vs. 100 benign
   controls (4:1), chosen to give every family the exact count issue #35
   specifies rather than a balanced split — detector FPR figures use only
   the 100-row BCONTROL denominator, not the full benchmark, so this does
   not bias the reported FPR itself.
4. **BCONTROL rows only ever populate `AlertTitle`** (a numeric GUIDE field)
   with real content; the benchmark does not include real benign text in the
   other five targetable fields, so a detector's false-positive rate on
   genuinely free-text-bearing non-AlertTitle fields is not directly
   measured here.
5. **Benign and attack rows differ in surface form, not only in intent.**
   GUIDE stores its categorical fields as integer codes, so every one of the
   100 BCONTROL rows is a bare number, while every attack row carries
   natural-language (or encoded-natural-language) text. "Contains prose" is
   therefore an almost perfect separator on this benchmark, independent of
   whether the prose is adversarial. Two consequences, both of which bound
   how the results should be read: reported detector FPR is measured against
   benign inputs that no realistic detector would flag, so it is a floor
   rather than a representative estimate; and interrater κ on the blinded
   subset has an artificial ceiling (§4). Closing this needs benign controls
   that are legitimate free-text analyst prose — a v1.1 change to the
   generator, out of scope for v1.0 and not applied retroactively here,
   since changing the corpus after results are reported against it would
   invalidate the M3.2 comparison.

## Results summary (M3.2, issue #36)

Full per-family breakdown and mechanism notes:
[`docs/m3-2-detector-family-matrix.md`](m3-2-detector-family-matrix.md). Headline
figures, from `experiments/results/m3_2_learned_detectors.json` and
`m3_2_heuristic_detectors.json`:

| Detector | Coverage | ROC-AUC | Overall TPR | FPR on BCONTROL |
|---|---|---|---|---|
| L1 TF-IDF+LogReg | 500/500 | 0.1978 (500-row) vs. 0.46 (legacy 40-row sanity) | 3.25% | 10.0% |
| L2 Llama Prompt Guard 2 | 500/500 | 0.779 | 31.25% | 0.0% |
| L3 NeMo-style Groq self-check | 495/500 | 0.7949 | 58.99% (233/395) | 0.0% |
| H1 regex | 500/500 | — | 2.75% | 0.0% |
| H2 schema (AlertTitle/DetectorId subset) | 500/500 | — | 100% (subset) / 10.5% (overall) | 0.0% |
| H3 SOC-aware (new) | 500/500 | — | 91.25% | 0.0% |
| H-union (H1 ∪ H2 ∪ H3) | 500/500 | — | 96.75% | 0.0% |

**L1's negative-transfer sanity check held**: it reproduces the legacy 40-row
corpus's 0.46 AUC (within the ±0.05 tolerance) and drops to 0.1978 on the
500-row benchmark — confirming, at 12.5x the sample size, that the TF-IDF
detector carries no usable signal on this domain (issue #36's own
`≤0.55` bar for "confirms negative transfer at scale").

**L3's five unscored rows are a detector limitation, not a quota cap.** The
run reached 495/500. The five that remain (`F4_004`, `F4_026`, `F4_030`,
`F4_040`, `F4_053` — all encoded/obfuscated payloads) return an empty,
unparseable response from the model, reproducibly, across separate
invocations and after the rate limit that briefly affected one of them had
cleared. More budget will not resolve them, so its recall is reported over
the 395 attack rows it actually scored rather than assuming the missing five
would have been detected: 233/395. The 95% Clopper-Pearson interval in
`experiments/results/m6_3_ci_backfill.json` uses that same denominator.
`experiments/results/m3_2_learned_detectors.json`'s `l3.persistent_errors`
lists the five.

**L3 was L4 until 22 Sep.** An OpenAI Moderation detector occupied the L3
slot and was never run — no API key was provisioned, and the CNIT server that
would have hosted a local deployment is unavailable. On the supervisor's
instruction (issue #36) it is removed from the benchmark's scope entirely
rather than carried as a blank row, and this detector moved down to L3. Seven
detectors are reported here because seven were measured.

**The union of heuristic layers outperforms every learned detector here**
(96.75% TPR at 0% FPR) — including on families the issue's own text expected
to evade everything (F3, F6). This is reported as measured, not adjusted to
match that expectation; see `docs/m3-2-detector-family-matrix.md`'s
"Uncovered families" section for the honest reconciliation.

## 7. Recommended uses

Evaluating and comparing SOC-domain prompt-injection detectors; as a
regression fixture for a detector pipeline (see
`tests/test_guardrail_benchmark_regression.py`); as training data for a
detector explicitly scoped to this attack taxonomy, with the known biases
above disclosed to any downstream user.

## 8. Excluded uses

Not a source of real attacker signatures for a production intrusion-
detection system — it is a synthetic, template-generated corpus, not a
capture of real adversary behaviour. Not a substitute for the interrater-
validated release once the pending kappa pass (Section 4) completes; treat
the current release as v1.0-pre-validation until that number is committed.
